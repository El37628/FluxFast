# v1.0 fresh-consumer gate

PR 19 proves that a developer can build and start a representative FluxFast
application from the public documentation without an existing FluxFast project
or knowledge of repository fixtures.

## Authoritative input

[`docs/getting-started.md`](../getting-started.md) owns the backend and frontend
source used by the gate. Invisible `fresh-consumer:path` markers identify the
rendered code blocks; the test extracts those blocks directly instead of copying
an internal example project. A static release test rejects missing, duplicate,
or path-traversing markers and keeps the guide discoverable from the README.

## Isolated workflow

`pnpm run test:consumer:stranger` creates a temporary project outside the source
checkout and performs this workflow:

1. build and install the current Python wheel and npm tarballs into isolated
   Python and Node environments;
2. run the documented `create-next-app@16` command and `fluxfast init`;
3. write only the application source extracted from the public guide;
4. run `fluxfast types` and its read-only drift check;
5. run setup diagnostics, TypeScript checking, and the production build;
6. run strict production diagnostics;
7. start the supervised one-origin production service and verify both pages,
   the shared typed resource, protocol envelope, health, readiness, and graceful
   shutdown.

The generated schema is also inspected for the two documented pages, the
`site-summary` resource, the `increment_visits` mutation, its generated
`IncrementVisitsBodyValidator`, and its `incrementVisits` helper.

## Continuous evidence

The `Fresh documentation consumer` job in
`.github/workflows/release-smoke.yml` runs this workflow on every pushed branch
and pull request. The ordinary JavaScript and release-policy suites separately
check generated output, package builds, browser behavior, and the guide-to-gate
wiring.

This gate is deliberately narrower than PR 20. It proves onboarding from public
documentation with a small application; the next packed-candidate gate remains
responsible for all four release distributions, the complete runtime behavior,
and the distributed Redis consumer.
