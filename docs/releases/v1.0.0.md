# FluxFast 1.0.0 Release Notes

> **FluxFast 1.0 promotes the v0.9 contract to stable semantic-versioning
> guarantees.**

FluxFast 1.0 is a confidence release, not an architecture or feature reset.
The Python runtime, framework-neutral Core package, and Next.js adapter retain
the public behavior frozen in v0.9.0 after realistic use, mixed-version
rollouts, failure injection, lifecycle stress, security review, performance
comparison, and packed release-candidate validation.

## Stable contract

FluxFast 1.x now guarantees compatibility for:

- documented top-level Python exports and behavior;
- all `@fluxfast/core` root exports and all five supported
  `@fluxfast/next` package paths;
- Python and JavaScript CLI commands, meaningful flags, documented environment
  variables, generated filenames, and generated semantic exports;
- the unchanged `fluxfast/1` browser protocol, media type, headers,
  capabilities, envelopes, patches, redirects, and live events;
- the closed `fluxfast-schema/2` developer manifest, its fingerprint rules,
  and continued schema/1 reading; and
- documented resource, cache/scope, mutation, validation, deferred, live,
  one-origin production, health, readiness, and lifecycle behavior.

Package 1.0 does not introduce `fluxfast/2` or `fluxfast-schema/3`. Package,
wire-protocol, and developer-schema versions remain independent.

The complete boundary and evolution rules are in the
[stability contract](../stability.md), [versioning policy](../versioning.md),
and API inventories for [Python](../python-api.md),
[`@fluxfast/core`](../core-api.md), and [`@fluxfast/next`](../next-api.md).

## Corrective hardening since v0.9.0

The promotion fixes release-blocking edge cases without changing the stable
surface:

- late navigation, prefetch, deferred, live, mutation, history, logout, and
  destruction races retain the newest authoritative resource/session state;
- client state-only metadata and internal race history remain bounded, with
  canonical recovery after conservative eviction;
- FastAPI application lifespan state, owned cache/broker cleanup, Redis
  subscription I/O, supervised descendants, workers, and signal handlers clean
  up under concurrency, cancellation, failure, and process-parent exit;
- postponed, aliased, and `Annotated` FastAPI `Request` parameters retain
  application-owned authentication state;
- deeply nested known-version hints fail safely, initial SSR redirects remain
  on the configured backend origin, generated writes reject a symlinked project
  boundary, and dynamically nominated hop-by-hop headers are removed; and
- dependency/security scans fail closed, release actions remain commit-pinned,
  and verified distributions retain checksums and registry provenance.

The [final freeze audit](v1.0-final-freeze-audit.md) accounts for every runtime
source difference from v0.9.0 and records zero unresolved P0/P1 findings. A
version-normalized digest locks all 100 candidate runtime files during release
promotion.

## Compatibility and release evidence

The 1.0 candidate passed:

- a 600-cycle production application soak with SQLite persistence, multiple
  identities, live reconnects, restart recovery, and input/file integrity;
- both v0.9.0-to-candidate package upgrade orders, the matched candidate, and a
  complete same-project rollback to v0.9.0;
- Python 3.11–3.14, Node.js 22/24, minimum Next.js 16.3 with React 19.0, and
  latest compatible Next.js 16/React 19 consumers;
- Redis 6.2 and 8.10 integration, independent workers, shared cache reuse,
  cross-worker invalidation/live convergence, outage/restart, and isolation;
- same-origin development and production browsers, Docker, rootless Podman,
  and Docker/Podman Compose with Redis;
- controlled request/cache/code-generation/validation/bundle/memory/production
  comparisons against v0.9.0 in both workload orders; and
- CodeQL, dependency review, npm/Python audits, artifact-content verification,
  a public-documentation stranger consumer, and the exact four-distribution
  packed candidate.

The [final release-candidate gate](v1.0-final-candidate-gate.md) records the
exact tested commit and immutable workflow evidence for every matrix rung.
The [artifact and publication gate](v1.0-artifact-verification.md) records the

The release builds one wheel, one source distribution, and two npm tarballs,
records all four SHA-256 digests, publishes with trusted OIDC identities, and

## Supported runtime matrix

| Runtime | FluxFast 1.0 support |
| --- | --- |
| Python | 3.11, 3.12, 3.13, 3.14 |
| Node.js | 22, 24 |
| Next.js | `>=16.3.0 <17.0.0` |
| React / React DOM | `>=19.0.0` |
| Redis Open Source | 6.2 through 8.10 when Redis features are configured |

The supported production topology remains one public Next.js origin with
FastAPI supervised on a private loopback port. Multi-worker positive-TTL live
resources require both `RedisResourceCache` and `RedisLiveBroker`.

## Upgrade from v0.9

No application rewrite or initializer rerun is required. Upgrade the three
packages together:

```bash
python -m pip install --upgrade "fluxfast==1.0.0"
npm install @fluxfast/core@1.0.0 @fluxfast/next@1.0.0
```

Regenerate contracts, verify drift, typecheck/build, and run strict production
diagnostics:

```bash
fluxfast types backend.main:app --frontend frontend
fluxfast types backend.main:app --frontend frontend --check
npm --prefix frontend run typecheck
fluxfast build --app backend.main:app --frontend frontend
fluxfast doctor --production \
  --app backend.main:app \
  --frontend frontend \
  --strict
```

See the complete [v0.9 to v1.0 upgrade guide](../upgrade-v1.md), including
rollback. Matching versions remain the recommended production state.

## Responsibilities and known boundaries

Applications continue to own authentication, authorization, CSRF, trusted
proxy configuration, request-body/ingress limits, and secret handling. Cache
scope and live authorization derive from server-owned application identity;
browser metadata is never authority.

Redis Pub/Sub remains ephemeral and reconnects recover through canonical
resource reads. Generated artifact replacement is atomic per file rather than
a transaction across the entire generated set. POSIX/Linux process lifecycle
proof is stronger than Windows descendant-process proof. These documented
boundaries are unchanged and are not unresolved 1.0 release blockers.
