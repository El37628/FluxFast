# v1.0 adjacent compatibility gate

FluxFast 1.0 uses published v0.9.0 as its mandatory adjacent compatibility
baseline. The release-artifact workflow builds the current Python wheel and Core
and Next tarballs, then exercises these transitions in isolated consumers:

| Sequence | Mixed state | Matched state | Rollback |
| --- | --- | --- | --- |
| Python first | current-source Python + published JS 0.9.0 | all current-source artifacts | all published 0.9.0 |
| JavaScript first | published Python 0.9.0 + current-source JS | all current-source artifacts | all published 0.9.0 |

Each sequence begins with a matched published v0.9.0 consumer. Each baseline,
mixed, matched, and rolled-back state performs schema generation and its
read-only drift check, TypeScript checking, and a Next.js production build. It
then starts three independent Uvicorn workers behind the test proxy and a
production Next.js server against Redis.

The browser and diagnostics assertions cover:

- server-rendered blocking and deferred resource states;
- same-origin navigation and Back restoration;
- omission and reuse of an unchanged known resource in a navigation delta;
- a rejected mutation with a real HTTP 422 validation response;
- a successful generated or untyped mutation and scoped invalidation;
- deferred settlement and live synchronization across multiple clients;
- cache reuse, invalidation, and Pub/Sub delivery across separate workers; and
- clean process shutdown without browser exceptions.

Rollback reinstalls every package from the v0.9.0 registries, regenerates and
rebuilds the same consumer, starts it again, and confirms repeated `fluxfast
init` calls leave the scaffold unchanged. The workflow also keeps one
single-direction current-Python/JavaScript-0.8.1 distributed smoke as historical
evidence.

Before the version-preparation PR, current-source artifacts still carry the
repository's v0.9.0 metadata. Their file URL and tarball installation specs,
rather than their version strings, distinguish them from exact registry
installs. The tagged release workflow repeats both sequences after publication,
when the candidate has its final v1.0.0 registry identity.
