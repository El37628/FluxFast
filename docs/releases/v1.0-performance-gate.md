# v1.0 performance regression gate

Status: evidence collection in progress. This is not a completed release gate.

Compare the candidate with the existing `v0.9.0` tag, not merely with whichever
source the benchmark imports. Preserve the [recorded v0.9 freeze results](../benchmarking.md#v09-freeze-baseline-against-v081)
as historical evidence and rerun that baseline with matched tooling before
interpreting candidate differences.

## Repeatable same-harness comparison

Prepare a separate checkout of `v0.9.0` with the candidate's reviewed workspace
lock and Next/frontend development manifests. Install with the frozen lock and
use the same Python interpreter/environment. Do not modify baseline package
runtime sources. Start a disposable Redis instance, then run:

```bash
FLUXFAST_BENCHMARK_REDIS_URL=redis://127.0.0.1:PORT/15 \
  node benchmarks/scripts/benchmark_v1_comparison.mjs \
  --baseline /path/to/v0.9.0-checkout --output /path/to/new-forward-results
```

Repeat in the opposite order with a new evidence directory:

```bash
FLUXFAST_BENCHMARK_REDIS_URL=redis://127.0.0.1:PORT/15 \
  node benchmarks/scripts/benchmark_v1_comparison.mjs \
  --baseline /path/to/v0.9.0-checkout --output /path/to/new-reverse-results \
  --reverse
```

The runner verifies the baseline tag, rejects self-comparisons, requires matched
workspace manifests/lock and dependency versions, checks actual Python module
ownership, and builds each selected package tree. It records source and harness
SHA-256 fingerprints, per-workload logs, exit status, and correctness results in
`comparison.json`. It refuses to overwrite an existing evidence directory.
Final source/harness checks reject changes during measurement.

Each workload runs sequentially against both sources:

- Requests: 25 fresh applications with cold, mixed known-version, and warm
  cache phases; exact loader counters, payloads, and omission checks.
- Deferred settlement: five comparisons with fixed 10/100/500 ms loaders;
  initial/follow-up timings, counts, and payload tradeoffs.
- Live: 50 latency samples, a 10,000-event slow-client flood, and 500 repeated
  connections; canonical refresh, bounded queues, and exact cleanup.
- Redis: ten samples per 1/10/100/1024 KiB payload, tag invalidation, and 64 warm
  HTTP requests at each 1/2/4/8-worker topology; exact cross-client values,
  cold/warm loader counts, and known-version omissions.
- Codegen: all ten contract/resource/nesting/route/mutation workloads with five
  samples for schema export, parsing, type/validator generation, TypeScript
  compilation, doctor, and generated-drift checks.
- Validation: ten samples of 100 validations for each nested, recursive, and
  10,000-object valid/invalid-tail workload; exact accepted/rejected paths.
- Memory: five samples after warm-up, including 100-cycle navigation, deferred,
  mutation, reconnect, and long-lived mixed lifecycles; hard candidate
  state/connection/listener/epoch bounds remain mandatory.
- Bundles: matched production builds for minimal Core, minimal Next, no
  validators, one validator, and realistic validators/live/forms consumers;
  exact imported-plan retention and absent unused plan/runtime markers.
- Production: three start/readiness/SIGTERM cycles at each 1/2/4/8-worker
  topology; public/loopback boundary, exact workers, causal readiness,
  closed sockets, and process cleanup.

The missing-checkout regression verifies all JavaScript comparison benchmarks
honor the selected source instead of silently falling back to the candidate.
The historical v0.9 state-only memory defect is reported explicitly only when
all legacy scenarios finish and growing long-lived metadata fails its exact
bound assertion. It is not reported as a clean baseline result. Unexpected
baseline errors and every candidate correctness failure remain fatal.

## Local comparison results

Local forward and reverse comparisons completed on 2026-09-24. The baseline is
the `v0.9.0` tag at `ee50ce0276c713a066e9324e3a9e5d2fc6df3872`; the candidate
runtime is `d28a8d93500260dc8680a03b180f0e04e0e3ecb0`. Both checkouts used Node
24.19.0, Python 3.13.14, Next.js 16.3.4, React/React DOM 19.2.8, identical
Python dependency versions, and Redis 8.10.1. The host was a 12-vCPU Ryzen 5
3600 under WSL2. Raw outputs, environment metadata, source fingerprints, and
per-workload hashes were preserved in the [forward run](evidence/v1.0-performance-2026-09-24/forward/comparison.json)
and [reverse run](evidence/v1.0-performance-2026-09-24/reverse/comparison.json),
along with every workload's text output. Additional 50-sample Redis and
10-sample memory follow-ups are recorded in
[follow-ups.md](evidence/v1.0-performance-2026-09-24/follow-ups.md). The manual
GitHub workflow will publish a CI artifact from the PR head.

The early 1 MiB Redis sample prompted a 50-sample rerun. The initial reverse
request/cache pass also showed a >10% timing increase; three alternating
100-sample runs did not reproduce it. These follow-ups and the final
forward/reverse comparisons show no repeatable large-payload read or request
regression. Other payload sizes and multi-worker HTTP results varied with run
order; exact correctness checks remained stable.

The local evidence satisfies the comparison and investigation portions of this
gate. Remaining work is to run the checked-in manual comparison workflow on
the PR head, retain its uploaded artifact, pass all required PR checks and
review, and complete the protected merge/synchronization workflow. Host timing
and heap values remain observations, not flaky CI gates. Correctness, payload
identity, state bounds, and tree-shaking checks fail hard.

This work changes benchmark tooling and release evidence, not the frozen
public API, wire protocol, schema, or deployment model.
