# v1.0 client lifecycle and retained-state gate

The promotion gate exercises long-lived routers, not only short-lived objects
that garbage collection can reclaim wholesale. Core remains framework-neutral;
the fixes add no public API, wire field, capability, or cache-scope change.

## Repeatable correctness workload

`packages/core/tests/client-lifecycle-stress.test.ts` exercises:

- 400 mixed navigation, prefetch, deferred-load, and mutation cycles with unique
  identities, inspecting resource/page/prefetch bounds and settled controllers.
- 200 actual deferred navigation batches, inspecting resolved manifests and
  release of the batch's controller, keys, and captured epochs.
- 200 state-only pending/loading/error identities per variant, including ready
  values, recent metadata reads, eviction notifications, and unsubscription.
- More than 1,024 intervening identities while old resource, prefetch, and page
  work is pending. Eviction cannot make old state authoritative again.
- Canonical recovery when navigation loses a returned key or a known-version
  omission to eviction, without replacing newer ready/error/loading state.
- 200 history listener/subscription cycles, 200 live reconnect cycles, and
  200 router create/destroy cycles. Streams, network subscriptions, timers,
  listeners, controller ownership, and request bookkeeping return to zero.
- Reentrant logout/destruction from a visit-success listener cannot start an
  obsolete deferred batch. Resource/error/pending/page subscribers that close
  the session during envelope application also stop remaining old settlements.
  Resource-only loading and prefetch apply the same per-key session checks,
  including failure diagnostics and the loading transition itself.
- Logout/destruction between prefetch transport completion and router settlement
  cannot restore old session state or emit a late success diagnostic.

The Next adapter additionally performs 100 StrictMode provider remounts with
resource/status hooks. Exactly one logical stream remains active; unmount
clears batching timers and hook/network subscriptions; destruction releases
history and router-owned live listeners.

`tests/browser/frontend/e2e/live-flow.spec.ts` runs 20 live/history round trips
in Chromium. It tracks actual SSE requests and window online/offline/popstate
listener identities, requiring stable counts and no document reloads. The
development fixture enables React StrictMode. Production runs retain the same
navigation/cleanup proof, but do not claim StrictMode's development-only effect
replay is active in production.

## Corrections and tradeoffs

Loading/error metadata now participates in the same `ResourceStore`
`maxResources` LRU as ready values. Metadata reads refresh recency; eviction
notifies subscribers and removes state and stale bookkeeping together.
Subscriptions do not pin cache entries, matching existing value eviction.

Internal per-key race history is capped at 1,024 identities and cleared on
destruction. Evicted history contributes monotonic conservative watermarks,
separately for speculative and authoritative work. Forgetting a key therefore
cannot reset its authority to zero or let speculative eviction veto navigation.
These limits are internal implementation details, not new configuration APIs.

Under unusually high identity churn, conservative rejection can require an
extra canonical resource-only request. Navigation recovers missing keys through
the same server-owned page while retaining its shell. Uncertain history also
requires canonical recovery when only a speculative value is resident; it
cannot silently promote that value over the navigation's response. Newer
resident values, errors, and pending loads remain protected. A raced prefetch
envelope is marked unusable by weak identity, without retaining it or cancelling unrelated
prefetch-backed navigation. Rejection is scoped to the owning manager, reset
for fresh responses/session clear, and shared between the official CJS/ESM
builds. Frozen transport envelopes remain supported. Both module orderings
have regression coverage in `scripts/client-module-interop.test.mjs`.

## Retained-state observations

Observations below used the final benchmark script against the preserved
pre-fix `b158178` Core build before rebuilding the candidate, with Node 24.19.0.
For a repeat, build Core in an isolated baseline checkout and run the current
benchmark script with that package root:

```text
FLUXFAST_BENCHMARK_REPOSITORY_ROOT=/path/to/baseline-build node --expose-gc benchmarks/scripts/benchmark_memory.mjs --samples 3 --cycles 200
```

Then run the candidate with the same workload:

```text
pnpm benchmark:memory -- --samples 3 --cycles 200
```

The new long-lived scenario keeps one router through one warm-up and three
samples: 800 total mixed cycles, four unique epoch identities per cycle, with
forced collection between samples. Its resource bound is 16 and page bound 8.

| Observation after 800 cycles | Before fix | Candidate |
| --- | --- | --- |
| Epoch identities | 3,200 | 1,024 |
| Resource state snapshots | 816 | 16 |
| Ready records | 16 | 10 |
| Heap retained after warm-up | +461.2 KiB | +187.0 KiB |

The before-fix benchmark fails its metadata bound. The candidate passes all
collection-size, state, prefetch cleanup, and destroy assertions. Candidate
epoch/state counts stay at 1,024/16 in each of the three observed samples.
The shared LRU intentionally trades some ready-value residency for bounded
loading/error metadata. Heap numbers include cache fill and runtime noise:
they are diagnostic observations, not exact-byte CI thresholds or a general
performance guarantee. The full performance comparison remains a later gate.

protocol baselines. No baseline or package version is rewritten for these fixes.
