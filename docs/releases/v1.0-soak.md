# v1.0 real-application soak — in progress

The accelerated production workloads and evidence review have completed. The
PR merge remains pending; the measurements below describe the actual runs.

## Application and frozen runtime

The repository-owned Operations Board is a functional SQLite-backed application
with two tenant workspaces, three cookie-authenticated identities, role/owner
authorization, and 60 initial work items. It has eight page components, task
creation/editing/status/deletion/discussion, profile changes, uniqueness and
assignment business rules, shared scoped resources, generated domain types and
validators, deferred reports/activity, and live synchronization.

The initial isolated consumer uses only published `fluxfast==0.9.0`,
`@fluxfast/core@0.9.0`, and `@fluxfast/next@0.9.0`. It is created in a fresh
temporary directory outside the source checkout, with a separate Python
environment and independently installed npm packages. The seed credentials are
public test data; this application is not production authentication guidance.

The local preparation and short trial used Node 24.19.0, Python 3.13.14,
SQLite 3.45.1, Next.js 16.3.4, React 19.2.8, and Playwright 1.62.1. The isolated
Python environment resolved FastAPI 0.141.1, AnyIO 4.15.1, Starlette 1.6.0,
Pydantic 2.13.5 / pydantic-core 2.46.5, and Uvicorn 0.52.4. These are actual
registry resolutions, not a claim that all Python transitive ranges are pinned.
The full raw report records every installed Python distribution. This application
uses one FastAPI worker with memory cache/broker. Distributed Redis evidence is
a separate consumer shape; it must not be inferred from this application.

## Workload evidence to record

- Starts/restarts and deployments, including preservation of stored edits and
  deletions across supervisor restarts.
- Navigations, history restores, and actual prefetch requests.
- Mutations, native validation blocks, authoritative validation rejections, and
  canonical convergence across two clients in the same tenant.
- Authenticated/anonymous transitions and a different tenant's unchanged data.
- Live stream opens/rotations/reconnects and recovery to canonical state.
- Supervisor/backend/frontend memory samples after warmup and repeated cycles.
- Browser exceptions, unexpected response failures, console/server warnings,
  generated-input hashes, and shutdown/orphan-process checks.

The preferred 7–14 day duration remains a target, not a substitute for meaningful
use. An accelerated run must state its actual elapsed time and workload; it
must not be described as a multi-day soak. No release-readiness conclusion has
been drawn yet.

## Short-trial evidence — not the exit gate

The two-start trial completed four full business cycles, 30 successful mutations
(including persistence sentinels and profiles), 31 link navigations, eight
history restores, ten ordinary auth transitions, and six cross-tenant checks.
It observed 33 actual prefetch requests, 68 resource-only requests, 107 requests
with known versions, and omission of ready resources on page responses. Both
static different-tenant pages rotated their live stream and recovered connected.
Both supervisors shut down with exit 0 and no owned child remaining. No browser
exception, unexpected HTTP failure, or changed frontend/generated input was
observed. The four intentionally asserted HTTP 422 responses each emitted the
browser's corresponding resource-error diagnostic; these are logged, not hidden.

The first passing trial took 25.172 seconds. A subsequent passing trial with
the explicit slow-hydration reproduction took 27.820 seconds. Neither is a
multi-day soak. Raw local trial reports are retained outside the checkout;
both full 600-cycle workloads subsequently completed successfully.

### Memory observations and limits

Aggregate server RSS at cycle 120 and cycle 200 was respectively 463,708 →
464,484 KiB, 443,940 → 446,092 KiB, and 439,116 → 440,468 KiB across the three
starts. Earlier samples showed allocation and reclamation, including drops
from 418,228 to 358,684 KiB in start 1 and 451,900 to 354,868 KiB in start 3.
The late samples approached a plateau; process counts stayed constant.
Browser heap samples also rose and fell, with final values approximately
26.5, 17.5, and 9.6 MiB. These observations do not prove retained-heap bounds
or behavior over days. The dedicated lifecycle/memory phase remains required.

## Exit review

The same-session review found no unresolved P0/P1 in this change. The recorded
incidents have application or harness explanations and regression coverage.
The workload observed canonical state after every task mutation, enforced
tenant boundaries, preserved edits/deletions across restarts, recovered normal
live rotations, preserved generated inputs and shut down every owned process.
RSS allocation/reclamation and late plateaus were consistent across repeated
starts; no increasing process count or unexplained monotonic growth was observed
in this workload. The realistic application and the two separate consumer
shapes above supply the evidence for PR 5.

This accepts the accelerated application exercise, with its stated 14-minute
duration and measurement limits. The dedicated concurrency, retained-memory,
server lifecycle, distributed and final release gates in later phases remain
required. Runtime sources and package manifests have no change from v0.9.0.
PR 5 can merge only after all required checks pass on its final commit.
