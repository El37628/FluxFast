# v1.0 server lifecycle final stress gate

This gate retains the frozen application, CLI, worker, cache-scope, and protocol
contracts. It corrects shutdown ownership without adding public configuration,
changing the production topology, or replacing Uvicorn's worker management.

## Application and dependency lifetime

`test_app_lifecycle.py` covers 100 independent startup/shutdown cycles and:

- The existing default FastAPI lifespan and custom application lifespans,
  including preservation of yielded request state.
- Readiness after successful startup and loss of readiness before teardown.
- Custom startup/shutdown exceptions without skipping owned dependency close.
- Multiple/concurrent close calls, including a blocked broker: other callers
  cannot return while cleanup is still pending.
- Cancelled AnyIO shutdown and a reentrant close from the cache itself.
- Broker-before-cache cleanup, sync/async optional cache close, and cache cleanup
  even when broker close raises.

`test_server_dependency_lifecycle.py` separately covers cache/broker ownership,
100 cancelled Redis subscriptions, a pending subscription handshake, cancelled
memory-broker close, reentrant Redis client close, and partial Pub/Sub close
failure. All other owned subscriptions and the owned client still receive
cleanup before the first failure is propagated. Externally supplied Redis
clients are never closed merely because their FluxFast wrapper closes.

Close serialization uses instance-owned locks. Same-task reentry returns without
waiting for itself; separate callers wait for the cleanup owner. AnyIO shielding
protects cleanup from cancelled request/task-group scopes, not from forced OS
termination or a dependency that never returns.

## Real process ownership

`test_server_lifecycle_stress.py` uses real subprocesses, not only fake process
objects. Its fixtures exercise:

- Backend and frontend crashes, with a living descendant that ignores SIGTERM.
- Descendant shutdown after the direct parent has already exited, and after a
  shutdown timeout with both parent and descendant ignoring SIGTERM.
- Development cleanup with both living and already-exited direct parents.
- Backend/frontend startup timeouts, cleaning every process already started.
- Sixteen complete supervisor signal cycles: development/production ×
  SIGTERM/SIGINT × four cycles. Children stop and handlers are restored.
- A second signal during a stubborn child's shutdown cannot interrupt sibling
  cleanup; injected stop failures also cannot skip the backend or handler reset.
- Actual development/production startup failure, restoring signal handlers and
  preventing frontend startup when the backend never listens/becomes ready.
- A real two-worker Uvicorn application, independently shut down with SIGTERM
  and SIGINT. Both worker PIDs disappear and both workers record application,
  broker, and cache teardown. The frontend sibling stops too.
- 100 short-lived process owners, repeated teardown, and garbage collection:
  weak completed-tree bookkeeping does not retain those process objects.

A separate Linux subprocess enables the kernel's subreaper behavior only in
the test harness. This reproduces PID-1 adoption without changing the host or
production process configuration. The harness confirms adopted descendant PIDs
have been reaped before it exits; relying on the host's init to hide zombies
would fail this assertion.

Production and development share an internal process-tree stop helper. It sends
SIGTERM to the isolated owned group, waits within the existing graceful deadline,
then sends SIGKILL and waits/reaps within the existing kill fallback. Reaping
uses only the group's adopted children after the direct child has been waited
for. Successful teardown is remembered weakly so repeated shutdown cannot
signal a stale completed group identity. Stop errors do not skip sibling cleanup.

The native signal/group tests require POSIX; the isolated adoption test requires
Linux. This is not new proof of equivalent descendant handling on Windows.
Processes deliberately detached from the owned group remain outside this
existing supervision boundary.

## Actual Redis connections

`test_live_redis_integration.py` runs 16 application lifespan cycles with owned
real Redis cache/broker clients. Each establishes at least three uniquely named
connections (cache, broker health, and Pub/Sub). After shutdown and repeated
close calls, Redis `CLIENT LIST` must contain none of that cycle's connections.
Subscription, pending-handshake, and active-I/O bookkeeping must all be empty.
The test creates no global Redis flush or infrastructure restart.

This check caught a race that collection counters and mocks did not: redis-py
can reconnect a read's locally retained connection after concurrent Pub/Sub
close has released it to the pool. Shutdown now cancels the subscription's
in-progress handshake/read before closing Pub/Sub and the owned client.
Those internal cancellation scopes cover I/O only, never an async-generator
yield; consumers may continue to use the existing iterator contract.
`subscriber_count` still counts established subscriptions, not pending
handshakes, so waiting for a subscriber before publishing remains meaningful.

## Repeatable verification

From the repository root:

```bash
./.venv/bin/python -m pytest -q python/fluxfast/tests/test_app_lifecycle.py python/fluxfast/tests/test_server_dependency_lifecycle.py python/fluxfast/tests/test_server_lifecycle_stress.py
FLUXFAST_TEST_REDIS_URL=redis://127.0.0.1:6379/15 ./.venv/bin/python -m pytest -q python/fluxfast/tests/test_live_redis_integration.py -k 16_application_shutdown
FLUXFAST_TEST_REDIS_URL=redis://127.0.0.1:6379/15 ./.venv/bin/python -m pytest -q python/fluxfast/tests
./.venv/bin/ruff check python/fluxfast
pnpm test:e2e:production
```

Use a local test Redis database for the example URL. The real connection test
uses unique client names/namespaces and only operates on its own identities.
The existing restart test additionally requires the explicit test-container
setting and is otherwise skipped; lifecycle proof does not stand in for the
separate distributed-runtime, security, container, or release-candidate gates.
