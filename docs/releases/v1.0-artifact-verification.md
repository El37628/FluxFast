# v1.0 artifact and publication verification

Status: pre-publication verification complete. Registry publication remains a
tag-triggered operation after this gate merges.

## Exact payload contract

FluxFast 1.0.0 has one accepted release payload:

```text
python/fluxfast-1.0.0-py3-none-any.whl
python/fluxfast-1.0.0.tar.gz
npm/fluxfast-core-1.0.0.tgz
npm/fluxfast-next-1.0.0.tgz
SHA256SUMS
```

The verifier rejects missing or additional distributions and checks each
archive without extracting it to disk. Paths must be canonical, relative POSIX
paths; links, special entries, duplicate paths, oversized entries, and unsafe
package targets are forbidden.

Python wheel and source-distribution metadata must match `pyproject.toml`,
including the stable version, Python range, every base and optional dependency,
project URLs, license expression, author, and embedded README. The wheel must
ship the `fluxfast` console entry point. Both Python archives must contain the
exact source-file inventory and exact bytes from `python/fluxfast/src`, plus the
reviewed README and license.

Both npm manifests must match the source package's public metadata, exports,
dependencies, peer ranges, engine range, package paths, and executable CLI
target. Every declared export, main/module/type target, and command must exist.
The complete packed `dist` and `bin` inventories and their bytes must match the
reviewed builds; extra internal files are rejected. README and license bytes
must also match.

`SHA256SUMS` must contain exactly four lines in the canonical distribution
order, with the current digest and basename for each artifact. Extra entries,
missing entries, reordered or renamed paths, stale digests, and a symlinked
checksum file are rejected.

## Publication chain

The `v1.0.0` tag workflow retains this order:

```text
full reusable CI and packed-consumer gates
  -> build and verify four distributions once
  -> upload Python, npm, and checksum artifacts
  -> download and fully re-verify the immutable payload
  -> publish PyPI with trusted OIDC and PEP 740 attestations
  -> publish npm with trusted OIDC and provenance
  -> consume only registry packages in production and mixed-version tests
  -> download and fully re-verify the five-file payload again
  -> create the GitHub release with the reviewed v1.0 notes
```

Both registry jobs depend on the downloaded-payload verification barrier. The
GitHub release depends on successful publication plus the registry-backed
production and both v0.9/1.0 rollout-order checks. It cannot be created from a
failed, skipped, or partially published run. No long-lived PyPI or npm token is
used.

The GitHub release body comes from [`v1.0.0.md`](v1.0.0.md), and the title uses
the reviewed stable-release headline. The release command verifies that the
immutable tag already exists before attaching the wheel, source distribution,
both npm tarballs, and `SHA256SUMS`.

## Adversarial regression coverage

The focused verifier suite contains 18 tests. It accepts the complete payload
and rejects:

- wrong package names or versions;
- Python or npm dependency drift and npm peer-range drift;
- missing exports and Python or JavaScript command targets;
- unsafe links and unexpected top-level or internal files;
- same-path Python source or npm build byte changes;
- README or license mismatches; and
- checksum drift or extra checksum entries.

The release-workflow tests also require the pre-publication verification job,
both registry dependencies on that job, final GitHub payload verification,
commit-pinned actions, OIDC permissions, provenance/attestation configuration,
registry-backed consumers, and reviewed release notes.
