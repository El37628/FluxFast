# v1.0 production topology final gate

This gate proves the frozen v0.9 topology; it introduces no deployment mode,
public API, wire type, capability, schema, or generated-contract change. The
candidate retains its existing package version until the final release phase.

## Required paths and direct evidence

| Requirement | Direct evidence |
| --- | --- |
| Initial document and server-side private fetch | Chromium with JavaScript disabled receives HTML containing backend-defined blocking resource values. Its hydration marker stays false and it makes no FluxFast protocol requests. The installed Next server's catch-all uses `FluxNextPage` and its server-only FastAPI fetch. |
| Hydration | A JavaScript-enabled browser receives the unhydrated HTML, then the test application's effect changes the hydration marker to true without replacing its initial backend data. |
| Client navigation | Clicking a FluxFast link sends a public-origin `X-FluxFast: 1` GET, receives a page envelope, and displays the new component without a new document request. |
| Header-gated rewrite | The same `/rooms` public URL returns HTML for an ordinary request and protocol JSON with `X-FluxFast: 1`. Document requests do not carry the protocol header. |
| No standard CORS requirement | Browser document, asset, navigation, mutation, deferred and live traffic stays on the public Next origin; the protocol response requires no `Access-Control-Allow-Origin` header. |
| Installed supervisor | An isolated consumer outside the repository installs the Python wheel and both npm tarballs, resolves all three packages inside its own environment, then executes its installed `fluxfast build`, `fluxfast doctor --production --strict`, and `fluxfast start`. `PYTHONPATH` is empty. |
| Immutable startup and complete shutdown | Source/generated snapshots are unchanged after startup and browser execution; SIGTERM exits the installed supervisor with status zero, and both allocated runtime ports reject connections afterward. |
| Docker and rootless Podman | The same reference Dockerfile builds and runs under both engines. Tests inspect the actual image and container, exercise SSR/hydration, navigation, validation, mutations, live events and reconnects, then check clean SIGTERM shutdown. |

The repository browser test lives in `critical-flow.spec.ts`. The isolated
installed-artifact test lives in `scripts/test-next-init-live.mjs`, using a
test-only hydration marker in the consumer fixture. Neither marker is a
FluxFast API or generated artifact.

## Image gate

`scripts/test-docker-production.mjs` verifies the real running container, not
just its manifest:

- only `3000/tcp` is exposed and published;
- FastAPI actually listens on loopback `127.0.0.1:8123`, not all IPv4 interfaces;
- the unprivileged FluxFast supervisor is PID 1;
- the root filesystem is read-only, Linux capabilities are empty, privilege
  escalation is disabled, and no engine socket is mounted;
- public health/readiness have the minimal documented bodies and the engine
  health check succeeds;
- browser responses and runtime logs do not contain the fixture's unique
  environment-secret sentinel; and
- engine stop exits the complete service with status zero.

The container browser configuration now runs **both** critical and live-flow
tests. The runner marks this actual optimized image as production so the
production-only origin and health tests run rather than skip. This closes the
earlier single-image gate's missing live coverage: it previously ran critical
navigation/mutation tests only. Live coverage includes two-client convergence,
subscription teardown on navigation, canonical offline resynchronization,
deferred live refresh, patch verification and history restoration.

Podman is invoked as a local unprivileged host user; the runner verifies
`rootless: true` and refuses a remote daemon. The same image definition and
browser suite apply to Docker. Separate Compose gates retain the existing
one-application-container plus private Redis infrastructure topology.

## Repeatable verification

Run from a checkout with dependencies and Chromium already installed:

```bash
pnpm typecheck
pnpm test
pnpm test:consumer:production
pnpm test:e2e:production
pnpm test:container:docker
pnpm test:container:podman
```

Do not run source generation or frontend typechecking concurrently with the
production immutable-input guard: they intentionally regenerate inputs and
would contaminate its measurement. The clean consumer and OCI builds use their
own isolated copies and installed environments.
Run the production and single-image browser suites sequentially as shown:
their host-side Playwright runners share the frontend's test-result directory.

The installed consumer command builds and packs the current candidate when
`FLUXFAST_ARTIFACT_DIR` is absent. CI supplies separately built wheel/tarballs
through that variable, then runs the same consumer. It does not accept workspace
package resolution or an editable Python install as installed-artifact proof.

The `Container` workflow executes both engines on GitHub runners. Local WSL
verification uses real rootless Podman; Docker is unavailable there, so Docker
evidence must come from the successful candidate CI job, not a Podman alias.

Local candidate verification on 2026-09-13 passed the isolated installed-artifact
consumer, **21** production browser tests with the immutable-input guard, and
**17** rootless Podman image browser tests with no skips and clean engine stop.
`pnpm typecheck`, **285** Core tests, **302** Next tests, **49** tooling tests,
the exact public API baseline and schema compatibility gate also passed.
The installed consumer used Python 3.13 and Next.js 16.3.3; the image used Python
3.11 and Next.js 16.3.4. Both used Node.js 24.19.0 and the current candidate's
installed FluxFast 0.9.0 packages.

This gate is topology and lifecycle evidence, not a claim of a completed
security audit, durable event delivery, application-database health coverage,
or a published v1.0 release. The separate security and release phases remain
required.
