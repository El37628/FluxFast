# FluxFast 1.1.0 Release Notes

> **FluxFast 1.1 makes resource synchronization observable in development
> without changing its production semantics.**

FluxFast 1.1 introduces an optional Laravel Debugbar-style inspector for the
FastAPI, Core, and Next.js runtime. It correlates browser navigation with safe
server timing metadata so developers can diagnose cache reuse, loaders,
deferred work, mutations, live recovery, and protocol negotiation from one
bounded timeline.

Existing FluxFast 1.0 applications remain compatible. The `fluxfast/1` browser
protocol and `fluxfast-schema/2` developer manifest are unchanged, and an
application does not need to install DevTools.

## Install and enable DevTools

Upgrade the runtime packages together and add the optional development package:

```bash
python -m pip install --upgrade "fluxfast==1.1.0"
npm install @fluxfast/core@1.1.0 @fluxfast/next@1.1.0
npm install --save-dev @fluxfast/devtools@1.1.0
```

Mount the inspector inside the existing FluxFast provider:

```tsx
import { FluxDevtools } from "@fluxfast/devtools";

{process.env.NODE_ENV === "development" && <FluxDevtools />}
```

Enable server timings only in the development application:

```python
flux = FluxFast(app, debug=settings.environment == "development")
```

No router prop, second server, public FastAPI port, or CORS configuration is
required. The browser continues using FluxFast's same-origin transport.

## What the Debugbar shows

The collapsed bar summarizes the current route, resources, server cache hits
and misses, deferred/live state, latest request duration, and errors. The
expanded inspector contains:

- **Overview** — request and resource health at a glance;
- **Resources** — logical key, opaque version, state, source, timings, safe
  cache classification, scope type, TTL, deferred/live flags, and update reason;
- **Timeline** — correlated navigation, resource, cache, mutation, deferred,
  live, transport, server, and lifecycle observations;
- **Cache** — browser page-cache activity separated from server resource-cache
  hit/miss/bypass and known-version omission;
- **Mutations** — safe method/path, timing, patch operation counts,
  invalidations, live publication counts, and redirect classification;
- **Live** — connection state, invalidation/patch activity, reconnects,
  bounded-queue recovery, and canonical resynchronization;
- **Protocol** — `fluxfast/1` request context plus independent diagnostic trace
  status, advertised capabilities, known versions, partial keys, and safe
  response counts.

The panel supports bottom/right docking, system/light/dark themes, keyboard tab
navigation, resize controls, the `Alt+Shift+D` shortcut, persistent UI
preferences, and safe trace copying. Diagnostic history defaults to 500 events
and has a hard 5,000-event maximum.

See the complete [DevTools guide](../devtools.md) for setup, panel semantics,
security exclusions, SSR behavior, performance bounds, and troubleshooting.

## Separate diagnostic protocol

DevTools does not add fields to a page, mutation, or resource envelope. An
active development subscriber opts into a separate channel:

```http
X-FluxFast-DevTools: 1
X-FluxFast-DevTools-Trace: <bounded-base64url-json>
```

The backend responds only when `FluxFast(..., debug=True)` and the request
header is exactly `1`. The decoded trace identifies
`fluxfast-devtools/1`, independently from package and application protocol
versions. It is capped at 7 KiB, drops lower-priority rows before the cap,
marks truncation, and never causes the application response to fail.

The initial SSR request uses the same validated trace and publishes it once
after browser hydration, including under React StrictMode. It remains separate
from `PageEnvelope` and is absent in production.

## Security boundary

Diagnostics contain only bounded execution metadata. They exclude resource and
patch values, request/mutation bodies, cookies, authorization/CSRF/custom
headers, query strings, scope fingerprints, user or tenant IDs, cache keys and
tags, client IDs, broker topics, connection URLs, redirect destinations,
arbitrary exception messages, and tracebacks.

A forged opt-in header cannot enable production diagnostics. The server debug
setting remains authoritative, metadata is sanitized again in the browser, and
the copied `fluxfast-devtools-export/1` trace uses the same value-free
projections as the UI.

## Production and performance guarantees

The npm package publishes conditional entries: development resolves the full
inspector and production resolves an inert `FluxDevtools` component. A normal
production runtime sends no diagnostic header, retains no diagnostic timeline,
creates no DevTools UI, and opens no extra live connection.

The release gates compare the inactive runtime with v1.0.1 in both benchmark
orders and require any regression above 1% to be repeatable beyond measured
noise. They also prove:

- a 1,000-navigation, 1,000-resource-update, 500-mutation, and 100-live-reconnect
  stress run stays inside its event, serialization, heap, resource, listener,
  and connection bounds;
- production builds contain no DevTools UI markers; and
- the equivalent Next.js route-size delta is at most 512 bytes.

## Package and release contract

FluxFast 1.1 synchronizes four package versions:

```text
fluxfast             1.1.0
@fluxfast/core       1.1.0
@fluxfast/next       1.1.0
@fluxfast/devtools   1.1.0
```

The release payload now contains one Python wheel, one Python source
distribution, and three npm tarballs. Its verifier requires all five at 1.1+
while preserving the exact historical four-distribution expectation for 1.0.x.
All files receive SHA-256 digests; registry publication uses trusted OIDC,
provenance/attestations, clean packed consumers, and v1.0.1 adjacent-version
upgrade and rollback checks before the GitHub release is created.

## Compatibility and upgrade notes

- Existing applications may upgrade Python, Core, and Next without mounting
  DevTools; no generated artifact or application rewrite is required.
- Regenerate and check typed artifacts after upgrading as usual.
- `@fluxfast/devtools` peers require Core and Next `>=1.1.0 <2.0.0`.
- Do not expose a private backend port for DevTools. It follows the same-origin
  Next.js transport already used by the application.
- Do not enable Python debug mode in production merely because the component's
  production entry is inert.

Recommended upgrade verification:

```bash
fluxfast types backend.main:app --frontend frontend
fluxfast types backend.main:app --frontend frontend --check
npm --prefix frontend run typecheck
fluxfast build --app backend.main:app --frontend frontend
fluxfast doctor --production --app backend.main:app --frontend frontend --strict
```
