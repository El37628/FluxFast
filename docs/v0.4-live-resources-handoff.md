# FluxFast 0.4 Live Resources implementation handoff

Status: active implementation plan.

FluxFast 0.4 adds server-pushed synchronization to existing resources. A
resource declared with `live=True` remains an ordinary resource: its loader is
the source of canonical state, its value stays in `ResourceStore`, and existing
resource hooks re-render when that value changes. Live events are only signals
to patch optimistically or reload canonical state.

The protocol remains `fluxfast/1`. Every live wire behavior is additive and is
enabled only when the client advertises the `live-resources` capability.

The normative design inputs are the [live protocol draft](protocol.md#draft-live-resources-extension-target-fluxfast-04)
and [fetch-SSE transport decision](decisions/0004-live-resource-transport.md).

## Non-negotiable boundaries

- FastAPI continues to own routes, authentication, authorization, resource
  declarations, and scopes.
- The browser sends logical resource keys only. It never supplies cache scopes,
  tenant IDs, user IDs, or internal broker topics.
- Opening a live stream reconstructs the authoritative page and runs its
  dependencies, but does not execute resource loaders.
- `@fluxfast/core` owns live connection and resource synchronization logic and
  remains free of React and Next.js imports.
- `@fluxfast/next` owns only framework integration, the status hook, and
  same-origin transport configuration.
- Resource values remain in the existing `ResourceStore`; there is no parallel
  live-data store.
- Live invalidation preserves the current value, marks it stale, and reuses the
  existing resource-only request path for canonical refresh.
- Server-to-browser delivery uses fetch-based SSE. Client writes remain normal
  HTTP mutations; WebSockets are outside the 0.4 scope.
- All per-client queues and live-request metadata are bounded.
- Redis is optional, but production multi-worker synchronization must use a
  shared broker rather than the in-memory broker.

## Security and correctness gates

The release is blocked until automated tests prove all of the following:

- a browser cannot subscribe to undeclared or non-live resource keys;
- stream creation reruns page dependencies and never runs resource loaders;
- user and tenant topics cannot cross authorization scopes;
- topic identifiers and browser events expose no raw scope data;
- logout and navigation close obsolete authenticated streams;
- reconnect performs canonical resynchronization;
- a slow client cannot grow server memory without bound;
- duplicate, unknown, and malformed events cannot corrupt `ResourceStore`;
- deferred/live and mutation/live races preserve the newest authoritative work;
- mutation origin suppression prevents redundant self-refresh while other tabs
  still converge;
- Redis carries events between workers and cleans up after failure/restart;
- non-live applications and mixed 0.3/0.4 package pairings retain 0.3 behavior;
- a production-built clean consumer synchronizes two browser clients through
  the ordinary frontend origin.

## Release acceptance flow

The representative acceptance test uses two authorized browser contexts on the
same scoped page. Browser A performs a normal FluxFast mutation. The server
invalidates its scoped cache entry and publishes a live invalidation. Browser B
keeps the old value visible as stale, performs one resource-only refresh, and
renders the new canonical loader result without polling, page reload, a second
API, or custom frontend event handling.

Release CI must run Python, JavaScript, browser, Redis, security, artifact,
clean-consumer, mixed-version, and bounded-memory checks. The GitHub release is
created only after PyPI/npm publication and registry-backed compatibility tests
pass.
