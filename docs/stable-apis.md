# Stable APIs

Stable APIs are the default surface for application developers. Use them to
define FastAPI-owned pages and resources, generate frontend types, render data,
navigate, submit forms, and return mutation results.

"Stable" is a compatibility classification, not a claim that every stable
symbol belongs in every application. Most projects use a small set of Python
builders and Next.js hooks. The complete package inventories remain available
when you need a less common stable type.

If you are implementing a cache backend, transport adapter, protocol client,
live broker, or code generator, continue with the
[Advanced Stable APIs guide](advanced-stable-apis.md). Advanced Stable APIs
receive the same 1.x compatibility guarantee; they solve lower-level problems.

## Choose the API by the task

| I need to... | Start with | Usually used in |
| --- | --- | --- |
| Attach FluxFast to FastAPI | `FluxFast` | Backend startup |
| Define a server-selected page | `Page` and `@flux.page()` | FastAPI route |
| Load typed page data | `define_resource()`, `resource()`, and `scope` | FastAPI route or shared resource factory |
| Return an immediate client update | `mutation()` and a patch helper | FastAPI mutation route |
| Render a resource | `useResource()` or `useDeferredResource()` | Client component |
| Inspect loading, stale, or error state | `useResourceState()` | Client component |
| Navigate without a document reload | `Link` or `useRouter()` | Client component |
| Submit and validate a form | `useForm()` with a generated validator | Client component |
| Configure the Next.js shell | `withFluxFast()` and `createFluxNextPage()` | Next config and catch-all page |
| Generate or check frontend artifacts | `fluxfast types`, `checkFluxFastProject()`, or `generateFluxFastProject()` | Development and CI |
| Validate an unknown value outside React | `createValidator()` or a generated validator | Framework-neutral code |

For a normal application, begin with the first eight rows. The setup and
generation APIs are normally written once by `fluxfast init` or invoked from
CI.

## Stable API families

### Python application APIs

| Family | Main APIs | What they are for |
| --- | --- | --- |
| Application integration | `FluxFast`, `Page` | Register page and mutation routes on a FastAPI application. |
| Typed resources | `ResourceContract`, `resource`, `ResourceSpec`, `ResourceLoader` | Declare a logical resource, its loader, and its cache/live behavior. |
| Reusable application types | `TypeContract`, `ContractMode` | Publish server-owned Pydantic contracts for generated TypeScript. |
| Cache isolation | `scope`, `CacheScope`, `ScopeType` | State whether a reusable value is public, per-user, per-tenant, or custom-scoped. |
| Mutation results | `mutation`, `replace_resource`, `merge_object`, `replace_item`, `remove_item`, `append_item` | Describe how the browser should update resources after a successful write. |
| Invalidation and redirects | `invalidate_resource`, `flux_redirect`, `flux_external_redirect` | Refresh canonical data or move the browser after a mutation. |
| Application errors | `FluxFastError`, `ResourceError`, `ResourceContractError`, `ScopeError` | Catch a documented failure at an application boundary when recovery is useful. |

FastAPI still owns authentication, authorization, request validation, database
transactions, and route dependencies. FluxFast result builders do not replace
those responsibilities.

### Next.js application APIs

| Family | Main APIs | What they are for |
| --- | --- | --- |
| Reading state | `usePage`, `useResource`, `useResourceState`, `useDeferredResource`, `useLiveStatus` | Subscribe a client component to server-selected page and resource state. |
| Navigation and writes | `Link`, `useRouter`, `useForm` | Navigate, mutate, validate, and display server/client validation errors. |
| Application shell | `FluxRoot`, `FluxProvider`, `defineFluxConfig`, `createFluxNextPage` | Connect the generated component registry to the runtime. Usually generated by `fluxfast init`. |
| Configuration | `withFluxFast`, `resolveFluxBackendUrl` | Install the same-origin server rewrite and resolve server-only backend configuration. |
| Generated registry | `checkFluxFastProject`, `generateFluxFastProject`, `generatePagesRegistry` | Detect or repair generated page-registry drift. Prefer the CLI in ordinary application scripts. |

Use generated resource keys, route helpers, mutation helpers, request-body
types, and validators from `src/.fluxfast`. They connect these APIs to the
FastAPI-owned contract without duplicating interfaces by hand.

### Framework-neutral Core APIs

Most React applications receive Core through `@fluxfast/next`. Direct Core use
is appropriate for framework-neutral validation, tests, or an adapter that
needs `FluxRouter`, its stores, events, patch helpers, and documented errors.

`createValidator()`, `refineValidator()`, and the `FluxValidator` interface are
the ordinary stable validation surface. Generated validators already implement
that interface, so application components normally consume a validator rather
than construct its plan themselves.

## End-to-end stable example

This example uses only the normal application surface. The backend owns the
room model, routes, resource loader, cache scope, and mutation authorization.

### 1. Define the backend page and mutation

```python
from typing import Literal

from fastapi import FastAPI
from fluxfast import (
    FluxFast,
    Page,
    append_item,
    invalidate_resource,
    mutation,
    resource,
    scope,
)
from pydantic import BaseModel, Field


class Room(BaseModel):
    id: int
    name: str
    status: Literal["available", "occupied"]


class CreateRoomInput(BaseModel):
    name: str = Field(min_length=1, max_length=80)


app = FastAPI()
flux = FluxFast(app)
ROOMS = flux.define_resource("rooms", list[Room])

rooms: list[dict[str, object]] = [
    {"id": 101, "name": "Garden", "status": "available"},
]


def room_resource():
    return resource(
        ROOMS,
        lambda: rooms,
        scope=scope.public(),
        ttl=30,
    )


@flux.page("/rooms", name="rooms")
async def rooms_page() -> Page:
    return Page(
        component="rooms/index",
        resources=[room_resource()],
        meta={"title": "Rooms"},
    )


@flux.mutation("/rooms", name="create_room")
async def create_room(body: CreateRoomInput):
    # Perform normal authorization and the database transaction here.
    created = {
        "id": 102,
        "name": body.name,
        "status": "available",
    }
    rooms.append(created)

    return mutation(
        patches={"rooms": append_item(created)},
        invalidates=[
            invalidate_resource("rooms", scope=scope.public()),
        ],
    )
```

The explicit public scope is safe only because this example contains no
private data. Use `scope.user(user_id)` or `scope.tenant(tenant_id)` after
normal FastAPI authorization for private values.

### 2. Generate the frontend contract

```bash
fluxfast types backend.main:app --frontend frontend
```

This produces the authoritative `resourceKeys.rooms`, `CreateRoomBody`,
`CreateRoomBodyValidator`, and `mutations.createRoom()` helper. Do not edit the
generated files.

### 3. Render and mutate from a client component

```tsx
"use client";

import type { FormEvent } from "react";
import { useForm, useResource, useRouter } from "@fluxfast/next";
import { mutations } from "@/.fluxfast/mutations.generated";
import {
  resourceKeys,
  type CreateRoomBody,
} from "@/.fluxfast/types.generated";
import { CreateRoomBodyValidator } from "@/.fluxfast/validators.generated";

export default function RoomsPage() {
  const router = useRouter();
  const rooms = useResource(resourceKeys.rooms);
  const form = useForm<CreateRoomBody>(
    { name: "" },
    { validator: CreateRoomBodyValidator },
  );

  async function submit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    if (!form.validate()) return;
    await mutations.createRoom(router, { body: form.data });
    form.reset();
  }

  return (
    <main>
      <h1>Rooms</h1>
      <ul>
        {rooms.map(room => (
          <li key={room.id}>
            {room.name}: {room.status}
          </li>
        ))}
      </ul>

      <form onSubmit={submit}>
        <label htmlFor="room-name">Room name</label>
        <input
          id="room-name"
          value={form.data.name}
          onChange={event => form.setData("name", event.target.value)}
        />
        {form.errors.name ? <p role="alert">{form.errors.name}</p> : null}
        <button disabled={form.processing}>Add room</button>
      </form>
    </main>
  );
}
```

Initial rendered output:

```text
Rooms
Garden: available
```

Submitting `{"name":"Lake View"}` produces a mutation envelope equivalent to:

```json
{
  "protocol": "fluxfast/1",
  "mutation": {
    "patches": {
      "rooms": [
        {
          "op": "append-item",
          "value": {
            "id": 102,
            "name": "Lake View",
            "status": "available"
          }
        }
      ]
    },
    "invalidate": ["rooms"]
  }
}
```

The patch renders the new item immediately. The invalidation marks it for a
canonical reload and deletes the matching public server-cache entry.

## Rules that keep application code on the stable path

1. Import Python names from `fluxfast`, Core names from `@fluxfast/core`, and
   Next.js names only from the documented package entry points.
2. Prefer generated resource keys, routes, mutation helpers, and validators to
   hand-written strings and duplicate TypeScript interfaces.
3. Let `fluxfast init` own the standard catch-all, transport, health, and page
   registry files. Customize their lower-level APIs only for a concrete
   integration requirement.
4. Treat scopes as data-isolation decisions. A cache TTL never makes private
   data safe to share.
5. Keep database writes and authorization in FastAPI. A mutation patch is a
   client update description, not proof that a write is allowed or persisted.
